# LMX Cloud — Roadmap

Original goal: go from working proof-of-concept (Phase 1-7) to something you can hand to strangers — developers trying it for free — without it breaking, leaking data, or embarrassing you. That base layer is done. The roadmap has since grown a second, bigger goal on top of it: reposition as Web3-native infrastructure and become "findable and payable" by autonomous agents (Phase 1 distribution, below). Both tracks are tracked in this one file — free-beta hardening didn't stop mattering, it's just no longer the only thing happening.

### Grid vs. Distribution — dependency and priority (decided 2026-07-28)

**The relationship, stated plainly:** LMX Grid (resource layer + tool/function layer, defined under Phase 2) is the core product. Distribution (Phase 1's three channels — x402 Bazaar/Agentic.Market, the MCP registry, the ElizaOS plugin — plus LMX.Agent) is the layer built on top of Grid and dependent on it: there is nothing to discover or call through any distribution channel that Grid doesn't first make real. This was always true structurally; it wasn't stated as an explicit priority ordering until now.

**What this changes, concretely:** once Phase 1's two remaining close-out gates clear (attorney review, ElizaOS live-agent test — unaffected by this decision, they close either way), near-term build energy goes to deepening Grid — Goal 1 (storage routing) and Goal 2 (callable function registry), i.e. Platform Sprint 1 through 6 — ahead of further distribution/demand-generation investment (Bazaar discovery-copy rewrites, curated-listing outreach, LMX.Agent Track A built out beyond a minimal working scaffold). This amends, not deletes, the 2026-07-17 "Demand generation... runs simultaneously alongside Platform Sprints 0-6, not after them" decision in the Demand generation section below — that call was right when it was made, when Grid was compute-only and thin. Now that Goal 2 is what actually makes Grid two-sided (third parties and agents listing functions, not just LMX routing its own compute), more distribution investment on top of a thin product returns less than the same effort spent deepening the product does. The historical record in "Demand generation" below stays as written; treat this note as the current call.

**What this does *not* change:** the already-shipped Phase 1 listings (Bazaar, MCP registry, ElizaOS plugin) stay live and passively discoverable — they're sunk infrastructure, not new investment, and Phase 2's own unpause trigger (a real unprompted x402 payment from a wallet LMX has never seen before, per the 2026-07-20 decision) can still fire opportunistically through them while Grid-deepening work happens. What's being deprioritized is *active new* distribution effort, not the channels that already exist. Goal 0/0b (compute reliability, resource-type breadth) also continue as-is — they were never gated behind the Phase 2 pause the way Goal 1/2 are, and this decision doesn't change that either.

**Named tension worth watching:** the Phase 2 unpause condition is itself a distribution outcome (an unprompted stranger payment), so distribution can't be deprioritized to zero — it needs to keep happening passively for that trigger to ever fire. If Grid-deepening work drags on long enough that the existing listings go stale (pricing, discovery copy, model catalogs) without any active tending, that trigger gets harder to hit, not easier. Revisit this balance if Platform Sprint 1-6 stretches past a few weeks without the unprompted-payment trigger firing.

### Storage, Vault, and LMX.Agent realignment (decided 2026-08-20)

**Context:** John is now working LMX Cloud daily around school and asked to realign the roadmap and sprints around four concrete goals rather than the abstract Goal 0→0b→1→2 sequencing below: (1) `lmx-tool-storage` and Vault working, (2) the full LMX.Agent framework built, with a marketing agent as the first agent on it, (3) continued demand-seeding on the inference router, (4) that marketing agent shipped as the first open-source `lmx.agent`, generating real Grid traffic. This section resolves the open questions that raised and gives the four goals one execution sequence with weekly checkpoints. It doesn't reopen or re-pause anything decided above — Track A already ran in parallel with Grid-deepening per the 2026-08-11 call (see Demand generation below); this extends that same parallel-tracks logic to storage and Vault specifically, and narrowly to Vault's early phases only.

**Decision 1 — what "storage" means now.** Goal 1 below ("Storage routing, the S3 of LMX") was originally scoped as routing agent file/data requests to decentralized networks (Filecoin/Arweave) — same pattern as compute. Separately, `CMO_AGENT_ARCHITECTURE.md` and `VAULT_PRIMITIVE.md` designed a different thing: `lmx-tool-storage`, a Postgres-backed metered KV/document store for agent state — `put`/`get`/`query` per namespace, now specced as markdown files with YAML frontmatter (frontmatter = structured/queryable fields, prose body + `[[wikilinks]]` = the graph an agent's memory forms over time). These were never the same build. **Resolved:** "storage" near-term (**Goal 1a**) means the Postgres KV/doc store — it's what Vault and LMX.Agent's `state.ts` actually depend on, and it's closest to buildable (Cursor prompt drafted 2026-08-18, needs amending to the markdown+frontmatter shape before use — see Goal 1 below). Filecoin/Arweave-routing keeps the name but becomes **Goal 1b** — durable/archival blob storage, a distinct and still-deferred later item, not to be conflated with agent memory again.

**Decision 2 — Vault is reopened, narrowly.** `VAULT_PRIMITIVE.md` was written specifically flagging that it reopens something this roadmap calls out of scope ("Explicitly not Phase 2: dataset marketplace... no anti-redistribution model exists yet," under Goal 2 below). That caution stands for Vault's later phases — registration/listing (Phase C), bond/slashing (Phase D), pooling (Phase E). What's reopened now is only Vault **Phase A** (storage foundation — own-namespace `put`/`get`/`query`, no gate, no settlement) and **Phase B** (paid cross-namespace reads + Merkle receipts, reusing the existing `anchors/` pipeline) — the same phased sequence already designed in `VAULT_PRIMITIVE.md`. Every agent gets a Vault by default at scaffold, same as it gets a Wallet — baked into `lmx-agent-template` itself, not an opt-in add-on.

**Decision 3 — the flagship agent is the marketing agent.** Resolves the "flagship demo-agent vertical" open question under "Phase 2 north star" below in favor of the third candidate (social/content/campaign-analysis) over agent-to-agent-commerce or DAO-monitoring — not just as a demo, but real dogfooding. This agent runs LMX's own `@LMXCloudio` account, doing the outreach work the daily demand-seeding checklist already calls for, while generating real Grid traffic (`generator.write_copy` inference calls, `lmx-tool-publish-x`, `lmx-tool-analytics-collect`) every time it posts. One build serves the framework proof-of-concept, the open-source flagship, and part of the demand-gen motion at once.

**Decision 4 — Vault's storage is federated/self-hosted, not LMX-custodied (decided 2026-08-21).** Decision 1 above named `lmx-tool-storage` as one Postgres-backed store; that was never actually weighed against LMX positioning itself as Web3-native infrastructure, and LMX being the literal custodian of every agent's vault contents contradicts that positioning. **Resolved:** split what was one thing into two. `lmx.storage` (package `lmx-tool-storage`) is the storage engine — same schema, same API surface Goal 1a already specs (markdown + YAML frontmatter via `gray-matter`, `put`/`get`/`query` per namespace) — but packaged as something each agent operator runs themselves (their own Postgres or SQLite, their own infra, a Docker image/one-command deploy), not one shared instance inside LMX's own `apps/tools/host`. What stays centrally hosted by LMX is only a manifest registry — `vault_id, owner_wallet, endpoint_url, permission_tiers, price` — no frontmatter, no body, no content, ever. A cross-vault read discovers the manifest through that registry, pays through Grid via x402 exactly as already designed, and Grid additionally issues a signed access grant the reading agent presents directly to the owner's own `endpoint_url` — LMX facilitates discovery and settlement, never proxies or stores the data. Own-namespace reads/writes get faster under this model, not slower: an agent's own vault calls never leave its own infra.

**What this reshapes below:** a *minimal*, non-public manifest entry (`vault_id, owner_wallet, endpoint_url, permission_tiers, price`) has to exist before Phase B's cross-vault reads have anywhere to point — resolvable only by an agent that already has the `vault_id`, not publicly browsable. That's narrower than what Vault Phase C was actually scoped as (public listing/discovery through Bazaar/MCP registry, still correctly deferred per "Explicitly not Phase 2: dataset marketplace" below) and doesn't reopen that caution — it just means the minimal registration plumbing now lands alongside Phase B instead of waiting for Phase C. Phase D (bond/slashing) also matters more under this model, not less: once LMX doesn't hold the data itself, the receipt trail and the economic penalty for redistribution become the primary enforcement mechanism, not a backstop on top of custodial control.

**Transition path, not a detour:** because `endpoint_url` is already an opaque pointer in this design, a fully decentralized backend (IPFS/Ceramic-style storage, Lit-Protocol-style threshold-encrypted access gated by an on-chain condition, so LMX never sees plaintext or holds keys) is a later swap of what's behind that same URL, not a rearchitecture — the point where Vault's storage model and Goal 1b's decentralized-storage ambition actually converge, see the Goal 1b note below.

**Decision 5 — semantic search added to Vault Phase A scope (decided 2026-09-02).** John restated the bar for `lmx-tool-storage`: it should be a complete, plug-and-play agent memory system, not just structured markdown+frontmatter storage — retrieval has to work on meaning, not only exact frontmatter-field filters. **Resolved:** semantic search is added to Phase A, not opened as a new goal. The existing `POST /:namespace/query` route (equality/containment over frontmatter fields, already built) stays for structured filtering; a new embedding-based search path is added alongside it, over the note body (and/or frontmatter) text. Still open, to resolve before a Cursor prompt goes out: which embedding source (LMX's own inference router — dogfooding Goal 0b's "vision, web search, embeddings" resource breadth — vs. an external embeddings API), which vector index per backend so the existing "zero-config SQLite default, Postgres for production" split stays intact (candidates: `sqlite-vec` for SQLite, `pgvector` for Postgres), and whether embeddings are computed synchronously on `PUT` or in a background job. This does not reopen `memory_store`/`memory_query`'s earlier deferral (see Goal 0b note above, "the natural pairing with embeddings... converges with Goal 1") — that note predicted this exact convergence; it's now realized inside Goal 1a specifically, not as a separate Goal 0b build. Week 1's **DONE** checkpoint below still stands for structured storage; semantic search is the remaining piece that makes it John's bar of "top-tier," not yet built.

**Decision 6 — two-tier symbolic/vector memory, local embeddings + Grid-routed consolidation by default (decided 2026-09-02).** Resolves Decision 5's open embedding-source question and gives Week 4's "reflection loop" (see Week 4 checkpoint below) a concrete design instead of a placeholder weekly job. **Two tiers, not one:** the existing markdown+frontmatter documents are the symbolic layer — canonical, curated, human-auditable, the thing Phase B actually sells; a new vector layer holds embeddings of raw/high-volume content, queried by similarity rather than by name. **Write path:** raw notes get embedded and stored continuously (cheap, local, no judgment call needed); a periodic consolidation pass (batched, not per-write) reads a batch of raw notes, decides what's durable, reconciles contradictions (supersede/annotate, never silently duplicate), and promotes the result into a symbolic "reflection note" — this is the two-layer note model from 2026-08-20 (data notes → reflection notes), finally given real mechanics. **Two different operations, two different defaults, not one on/off switch:** (1) embedding generation runs on every `PUT`, must stay local always — routing this through Grid would put an external call and a per-write cost on the "own-namespace reads/writes are free, ungated, local" invariant Decision 4 already made load-bearing, so this isn't optional; (2) consolidation is the periodic, judgment-heavy reasoning pass (reads a batch, writes a synthesized note) — this one defaults to routing through Grid via x402 (reusing the same call shape `agent.ts`'s recall→reason→remember loop already makes), with a pluggable interface (`EmbeddingProvider`, `ConsolidationProvider`) so an operator can swap either to a local model or their own API key. Turning consolidation fully local isn't a free toggle — it requires a real local-model implementation of `ConsolidationProvider`, and small local models are known to be markedly worse at contradiction/judgment calls than at similarity search, so full local-only mode is a second, harder build, not the default path. **New Grid-traffic source, not previously named:** a vault's own periodic consolidation pass becomes a recurring, self-generated Grid customer (an agent buying inference from itself to maintain its own memory) independent of the marketing agent's posting activity — worth tracking alongside Week 5's fork/star metrics once this is built. **Vector index:** `sqlite-vec` (the maintained successor to the now-deprecated `sqlite-vss`) for the SQLite default, `pgvector` for Postgres — confirms the choice flagged as a candidate in Decision 5. **Not yet resolved:** whether "fully local" needs to be a real, complete path before shipping (matching the sovereignty pitch as a hard promise) or ships later as an escape hatch once the Grid-routed default is proven — this decides whether the local `ConsolidationProvider` is in scope now or deferred.

**Decision 8 — fork-fund-run's actual revenue mechanism named; managed-service tier confirmed as the second rung (decided 2026-09-07).** Advisor-mode session clarified what "fork, fund, run" driving Grid traffic actually means for cashflow, since it had been getting treated as self-evidently "generates money" without naming the mechanism.

- **The mechanism isn't commodity inference margin.** Raw inference resale (the router) is true arbitrage — LMX has no cost advantage over the DePIN providers it routes to, so any markup is a tax a buyer can route around. Grid revenue from a forked agent's *tool calls* is structurally different: the chokepoint is platform access and data infrastructure a forker doesn't want to rebuild themselves (a registered/approved X/LinkedIn/Meta developer app, the persistent analytics store) — this is the same "real chokepoints, not the code itself" point already made in the open-core-tool-pattern reasoning, just now the explicit answer to "does fork-fund-run make money." A forker paying per-call through Grid to skip that friction is paying for something genuinely hard to replicate, not an arbitrary markup.
- **Two open items this surfaced, not yet verified:** (1) whether the settlement hook in the current template/tool code is actually hardened as non-optional — "hardwired to require Grid, not a convention someone can strip out," per the original open-core-pattern bar — needs checking before leaning on this as the revenue engine, not assumed from the design intent; (2) this revenue scales with fork adoption, which is currently ~0 (neither `lmx-agent-template` nor the marketing agent repo is public yet — see Week 4 below) — so this is a distribution problem right now, not a monetization-design problem.
- **Managed service confirmed as the second rung, not a competing idea.** Same two-buyer split already named in the open-core-tool-pattern note: self-serve forkers who'll do their own devops (fork-fund-run, Grid-metered), versus companies who'd rather pay a flat subscription and never touch a repo (the already-ranked #1 cashflow lever). Sequencing call: start this manually/white-glove (1-2 real customers, likely sourced through LMX Consulting's existing SMB/accounting-firm relationships) rather than building hosted multi-tenant infra before anyone has paid for it — the router/provider reliability is still not confirmed stable enough (see the still-open 2026-08-25 incident note above) to make self-serve hosted infra a good bet yet.
- **How to apply:** when reporting progress on "the money path," distinguish between fork/star counts (distribution signal) and actual settled Grid revenue from tool calls (the real number). Don't treat Week 3/4's marketing-agent build as the revenue event — it's the prerequisite that makes forking possible at all. The managed-service motion can start in parallel, manually, as soon as there's one working agent worth selling access to — it does not need to wait for Week 4's open-source ship.


### lmx.storage build roadmap (phases A0–E, added 2026-09-02)

Sequenced build plan for the `lmx-tool-storage` package specifically — the phased form of Decisions 4–6 above, not a change to any of them. Distinct from the six-weekly-checkpoint sequence below, which bundles storage with the template/marketing agent build; this is the storage package's own internal phase list.

- **Phase A0 — structured storage. DONE (2026-08-28).** Self-hostable Hono service, own DB per operator. Markdown+YAML frontmatter documents, byte-identical `PUT`/`GET`. `POST /:namespace/query` — exact/containment filter over frontmatter fields. Zero-config SQLite default verified end-to-end; Postgres path implemented but never live-verified (Neon project for this package still unconfirmed — the one real loose end from Week 1).
- **Phase A1 — semantic layer. DONE (2026-09-02).** `sqlite-vec` (SQLite, `vec0` table) / `pgvector` (Postgres, created on boot) as a sidecar vector index — the `documents` table/rows untouched. `EmbeddingProvider` interface with exactly one implementation, `LocalEmbeddingProvider` (`Xenova/all-MiniLM-L6-v2` via `@huggingface/transformers`, CPU ONNX runtime — Node builds of transformers.js v4 reject WASM), model warms at boot, weights cache under `data/models/`, no Grid call and no API key anywhere in the path, matching Decision 6's hard constraint. Every successful `PUT` embeds the document body and stores the vector. New route `POST /:namespace/search` (`{query, top_k?}`, default 10/max 100) returns ranked `{key, frontmatter, body, score}`; existing `POST /:namespace/query` and `PUT`/`GET` verified unchanged. Verified on SQLite: GET stayed byte-identical, filter query still correct, semantic query "when is the best time of day to publish?" ranked the right note first (~0.55) over an unrelated one (~0.22) with no shared keywords — the case exact frontmatter filtering structurally cannot answer. Empty query / bad `top_k` return 400; unknown namespace returns `[]`. Postgres/`pgvector` path implemented, not separately live-verified — same open item as Phase A0's Postgres path.
- **Phase A2 — consolidation / reflection loop. DONE (2026-09-02).** Built as a module inside `lmx-tool-storage` (not a separate package, per John's call). `ConsolidationProvider` interface (`src/consolidation/provider.ts`), one implementation `GridConsolidationProvider` (`src/consolidation/grid.ts`) — authenticates to Grid with `LMX_API_KEY` (Bearer), this vault's own credential, read from this package's own `.env` only; **not actual x402 signing** — a pre-funded-key call, same simplest tier as `lmx-agent-template`'s `identity.ts` tier 1, not the wallet/x402 tier. Local `ConsolidationProvider` implementation still doesn't exist — deferred as planned, Grid-routed is the only path. New route `POST /:namespace/consolidate` — a callable action, no in-process scheduler; operator wires their own cron. Pulls raw notes not already `kind: reflection` or already `superseded_by` something (oldest-first, capped at `MAX_CONSOLIDATION_BATCH = 40` so one Grid call stays in a reasonable context window), clusters near-duplicates locally via cosine similarity over the existing embeddings (`NEAR_DUPLICATE_THRESHOLD = 0.85`, union-find grouping, zero Grid cost for this part), sends clusters to Grid, writes one new `kind: reflection` note (itself embedded + searchable via the normal `PUT` path), and annotates every folded original with `superseded_by` pointing at the reflection's key — never deletes. A second call with nothing new to fold is a no-op (`message: "No unconsolidated notes in this namespace"`). Config check happens inside `consolidateNamespace()`, before the Grid call, not at boot — so `PUT`/`GET`/`query`/`search` stay zero-config regardless of whether `LMX_API_KEY` is set; missing key → 503 with an actionable error, other Grid failures → 502. **Verified live against the running vault:** four related/conflicting notes folded into one reflection (`reflection-2026-09-02T20-20-34-633Z`) that correctly called out a newer claim superseding an older one (morning now beats the earlier 2-4pm-weekday claim) and kept a durable fact (weekend engagement) rather than dropping it; the superseded original got `superseded_by` pointing at the new reflection. *Done when:* a week of raw notes produces one real reflection note, and a stale fact gets marked superseded, not duplicated — **met.**
- **Phase B — paid cross-vault reads. Unchanged scope, already specced above.** x402 gate on non-owner reads, Merkle receipt into the existing `anchors/` pipeline, minimal non-public manifest entry (`vault_id, owner_wallet, endpoint_url, permission_tiers, price`). *Done when:* a second agent pays to read a note, fetched directly from the first agent's own endpoint.
- **Phase C/D/E — deferred, unchanged.** Public listing/discovery, bond/slashing, pooling. `VAULT_PRIMITIVE.md`'s caution still fully applies to all three.

**Decision 7 — `lmx-tool-storage` extracted to its own public repo and embedded in `lmx-agent-template`; Vault permissions/monetization stay proprietary (decided 2026-09-02).** John's framing, stated directly: "lmx.storage [should be] open source so it can be preconfigured in agent.template. The thing we keep proprietary is vault[s'] permissions and monetization." Resolved same day:

- `lmx-tool-storage` (Phases A0-A2, everything built so far) extracted from this monorepo into its own public repo, `github.com/LMXCloud/lmx-tool-storage` — MIT licensed, installable as a real dependency (`pnpm add github:LMXCloud/lmx-tool-storage`), not npm-registry-published. A `prepare` script builds `dist/` on install (pnpm v10 requires the package be listed in the installer's `onlyBuiltDependencies` for that to run — documented in both repos). New `./server` export alongside the existing `.`/`./app` exposes a callable `start()`, and `LMX_STORAGE_DATA_DIR` lets a consumer point the SQLite file outside `node_modules`.
- `lmx-agent-template` now depends on it and starts it **in-process** by default (`src/embedded-storage.ts`) — `pnpm dev` is one command, one terminal, zero manual storage setup, unless `LMX_STORAGE_URL` is explicitly set to point at an external instance (e.g. Postgres in production). Still genuinely self-hosted per Decision 4 — it runs on whichever machine the agent runs on, not a shared LMX-run instance.
- **The real constraint this surfaced:** Phase B's access-grant check has to run inside whichever `lmx-tool-storage` instance is actually serving a cross-vault read — that's just where the data is. If the whole codebase is open source (as it now is), that gate is sitting in a fork, trivially deletable by anyone self-hosting their own copy — free storage *and* a free monetization-bypass in one download. So Vault permissions/monetization (Phase B onward: the x402 gate, access grants, manifest registry, pricing) **cannot be built into the open `lmx-tool-storage` codebase** the way Decision 4/6 originally implied — it needs a separate, closed layer that plugs into the open engine via some hook, not code shipped in the public repo. Not designed yet; needs resolving before Phase B starts, not after.
- **Known duplication, not yet resolved:** the original `apps/tools/lmx-tool-storage/` copy inside this monorepo was deliberately left untouched during extraction and still exists — two copies of the same code now, private and public, with no sync mechanism. Decide whether this monorepo keeps its own copy or depends on the new public package like everything else does.
- **Not yet independently verified:** a truly clean-clone test of `lmx-agent-template` (delete `node_modules`/`data`/`.lmx-identity.json`, fresh `pnpm install`, `pnpm dev` with zero env vars, zero other terminals) — asked of John, not yet confirmed run.

## Sprint — Payment-failure reconciliation — done 2026-07-28

Closes the last Phase 1 hard gate (POM section, Phase 1 close-out rollup): money moving with no result to show for it. `payment_events` already had `failed`/`refunded` statuses and `markFailed()`/`markRefunded()` implemented in `PostgresPaymentStore` — but `markRefunded()` was never called anywhere. Audit before building found four real gaps, not one generic one:

| Path | Money moves | Failure gap (before) |
|------|-------------|----------------------|
| x402 non-stream | CDP settle in `onAfterSettle` → `markSettled` | Inference errors in `chat.ts` catch didn't call `markFailed`/`markRefunded` |
| x402 | `tryClaimForFulfillment` before inference | Stuck in `fulfilling`; only surfaced via `payments.stuck` after 15m, never resolved |
| Balance non-stream | `deduct` after successful inference | Failures before `deduct` are safe — no debit ever happens |
| Balance stream | `deduct` after stream ends | Stream error after `deduct` left the customer debited with no credit-back |

**Design decision, automatic vs. manual:** balance credit-backs are always automatic (`CreditStore.credit` with `source: delivery_failure_refund` — reversing a credit deduction carries no external-money risk). x402 pre-settlement failures auto-`markFailed` (funds never left the payer, nothing to refund). x402 post-settlement failures auto-refund on-chain only when the amount is ≤ `REFUND_AUTO_MAX_USDC` (default $5) and a treasury signing key is configured; above that threshold or without a key, it queues `manual_required` in the ops hub rather than moving larger amounts unattended. A payment that settles but never links to a usage row queues a pending reconciliation and waits `RECONCILIATION_GRACE_MINUTES` (default 2m) before refunding — avoids refunding a response that actually succeeded but whose usage-recording just lagged.

**What was built** (`apps/api/src/payments/reconciliation/`): `service.ts` (reconciler — `reconcileX402Failure`, `reconcileBalanceCreditBack`, `executeManualReconciliation`), `logic.ts` (pure decision rules), `treasury-wallet.ts` (viem wallet client reusing the `anchors/poller.ts` signing pattern rather than new key-management), `poller.ts` (retries pending/failed reconciliations and stuck `fulfilling` rows), `store.ts` (new `reconciliation_events` table, migration in `migrate.ts`). Wired into `chat.ts` (x402 catch block + stream-error-after-deduct path), `x402-server.ts` (queues pending reconciliation on settle-without-usage), `server.ts` (poller startup/shutdown), and the ops hub (`payments.needs_refund` irregularity + `POST /v1/ops/reconciliation/:id/execute` + an Approve-refund button in `apps/ops`). `markRefunded` now also accepts the `completed` status. 50 tests added in `service.test.ts` (not independently re-run this session — worth a real `pnpm test` pass before relying on that count). Design doc at `docs/payment-reconciliation.md`.

**Config needed in production** (not yet set on Railway as of this writing): `TREASURY_PRIVATE_KEY` (treasury hot wallet, same address as USDC deposit receiving), `REFUND_AUTO_MAX_USDC` (default 5), `RECONCILIATION_ENABLED` (default true), `RECONCILIATION_GRACE_MINUTES` (default 2). ### Sprint Web3-2 — Verifiable on-chain logs (DONE 2026-07-07)

**Goal:** make LMX Cloud's routing/latency/cost claims independently verifiable, not just numbers displayed in a dashboard you control. Right now a skeptical developer has to trust `LogsPage.tsx`; Web3-2 lets them cryptographically check that a log entry hasn't been altered after the fact.

1. **Per-request receipt.** Hash the deterministic metadata fields of each `usage_events` row (provider, model, tokens, cost, latency, timestamp — NOT prompt/response content, metadata only, for privacy) into a receipt hash, stored alongside the row.

Historical log rows from before this ships won't be retroactively verifiable, only new ones going forward.

## Phase 1 distribution goal (decided 2026-07-06): "findable and payable" by autonomous agents

This replaces the old vague "Web3-3" stub. Phase 1 is done when an autonomous agent — zero human in the loop, no prior relationship with LMX Cloud — can discover LMX Cloud through at least one of three specific channels, pay per call in stablecoin, and get routed DePIN compute back. Everything before this point is infrastructure; this is the first point real, un-prompted revenue can show up.

**Why these three channels, in this order:** the first is protocol-level (works for any agent using the x402 payment standard, regardless of what framework built it), the second is the widest possible net (any MCP-compatible agent — Claude, ChatGPT agents, custom LangChain agents — not just crypto-native ones), the third is framework-specific and highest-touch, best used as a proof-of-concept case study once the payment plumbing from the first two is already working. Virtuals (ACP) is deliberately not in this list — its commerce layer is bespoke (on-chain jobs/escrow, not confirmed to run over x402), meaningfully heavier to build against, and not worth the lift until Phase 1 proves agents actually pay for this at all.

**Prerequisite that blocks all three goals: real x402 per-call payments.** Today's Web3-1 flow is deposit-then-spend-a-balance (fund an account, draw it down over many requests). x402 and the discovery layers built on it (Bazaar, Agentic.Market, MCP) expect pay-per-request: an agent gets an HTTP 402 response with a price, pays that specific call, gets the result. This is additive, not a replacement — the existing balance-funded flow stays for dashboard/human users. The new piece is a 402 response + payment-verification step on the paid inference routes, reusing the existing treasury wallet and `CreditStore` plumbing from Web3-1 rather than building new payment infrastructure from scratch.

### Goal 1 — x402 Bazaar + Agentic.Market listing

Build per-call x402 payment support on the inference endpoints (starting with `chat.ts`'s completions route), verify payment before routing to io.net/Akash as already built, then submit the resulting endpoint to Coinbase's Bazaar discovery catalog and to the Agentic.Market directory.

**Definition of done:** an agent with zero prior relationship to LMX Cloud finds it by searching Bazaar or Agentic.Market for inference/compute, pays for a single call in stablecoin, and gets a routed response back — no signup, no API key, no pre-funded balance.

### Goal 2 — MCP server

**Shipped (v1, 2026-07-09):** hosted Streamable HTTP MCP at `https://mcp.lmxcloud.io/mcp` with per-user `Authorization: Bearer lmx_...` passthrough, rate limits, and structured caller logging. Seven tools cover the full agent lifecycle on the existing balance-funded API:

| Tool | Purpose |
|------|---------|
| `get_status` | Provider health + fallback chain |
| `list_models` | Live model catalog |
| `get_pricing` | Full pricing catalog |
| `quote_price` | Single-call USDC estimate |
| `get_balance` | Caller credit balance |
| `get_usage` | Caller usage totals |
| `chat_completion` | Run inference (bills caller's key) |

**E2E validated:** external demo repo agent ran the full 6-step smoke suite (status → models → quote → balance → completion → usage) through MCP.

**Still open for Goal 2 "done":**
- Wrap the x402 per-call endpoint from Goal 1 (today MCP uses pre-funded API key balance, not pay-per-request stablecoin).
- Publish/discover in the MCP registry ecosystem (Bazaar listing gate still applies).

**Definition of done (full Goal 2):** any MCP-compatible agent can discover LMX Cloud through the MCP registry ecosystem and call it as a paid tool, using the same per-call payment flow as Goal 1.

### Goal 3 — ElizaOS plugin

Build a model-provider plugin against the existing OpenAI-compatible endpoint, with wallet-based key minting wired into plugin setup (reusing the raw-keypair mint flow already shipped in Web3-1 — no new auth work needed). Submit it to the `elizaos-plugins/registry` (an `index.json` entry via PR).

**Definition of done:** an ElizaOS developer installs the plugin, points it at a wallet or keypair, and their agent's inference is funded and routed through LMX Cloud with no manual signup step. Deliberately last — most framework-specific, best positioned as a reference case study once Goals 1-2 prove the underlying payment flow actually works.

**Explicitly out of scope for Phase 1:** Virtuals/ACP, Autonolas, Fetch.ai, Bittensor. Longer tail, bespoke integrations each — revisit only once Goals 1-3 show real traffic.

**Hard blocker, elevated again: Week 3 legal.** Going live on public discovery catalogs means strangers' autonomous agents transacting real stablecoin against LMX Cloud with zero signup and zero prior relationship — a materially bigger exposure than the free-beta dev signup Week 3 was originally scoped for. ToS, privacy policy, and acceptable-use content must close before or in parallel with Goal 1 shipping, not after.

**Success metric for Phase 1:** the first real, un-prompted x402 payment from a wallet LMX Cloud has never seen before, routed successfully to io.net or Akash and settled. That single event is the proof-of-life signal that distribution works — everything upstream of it is plumbing, not revenue.

**Native token — still deferred by design**, unchanged from before, after Phase 1 once there's real usage/treasury data. "Governance + economic rights" token language is securities-law surface area (Howey-test territory) — legal counsel before any public token language, not an engineering task.

**Open question, still unresolved:** does Phase 1 replace the current dev-first free-beta plan (Weeks 3-4 above), or run as a parallel track? Web2 (Clerk) and Web3 (wallet) users can coexist under Web3-1's design, but Week 4 outreach copy/channel choice should reflect whichever way this leans.

## Phase 2 — settlement + proof layer for the agent economy (revised 2026-07-11)

**What LMX Cloud is, directionally — the operating thesis this section builds from:** LMX Cloud is the settlement and proof layer for the agent economy — infrastructure that lets an autonomous agent with no human, no legal entity, and no corporate card discover a resource, pay for it per-call in stablecoin, and cryptographically prove it was delivered. Two layers, different competitive position each:

- **Execution layer, named "LMX Grid" (decided 2026-07-28)** (the "AWS" surface) — resource-agnostic routing via the `ProviderAdapter` pattern (`apps/api/src/providers/`): compute (io.net/Akash, done), storage (Filecoin/Arweave, Goal 1 below), and eventually third-party/agent-authored functions (Goal 2 below). LMX Grid has two sub-layers, not one: a **resource layer** (compute/storage/embeddings/etc. — what LMX itself operates and routes) and a **tool/function layer** (the MCP-callable interface over those resources, plus Goal 2's third-party function registry once it ships). Named "Grid," not numbered — the roadmap already uses L0/L1/L4/L7 for the separate long-term vertical-stack ambition under Phase 3, and numbering this "Layer 1/2" would collide with that.
- **Trust layer** (what's actually defensible) — settlement (x402 per-call payment) + proof (Merkle-anchored delivery receipts, Web3-2). Payment alone is not a moat — Coinbase's CDP Facilitator already owns that and LMX builds on top of it (`docs/x402-verification.md`). Discovery alone is not a moat — Coinbase's real CDP Bazaar already has the liquidity (165M+ cumulative x402 transactions, 480K+ agents, ~$50M+ volume as of April 2026, per Chainalysis / x402 Inc. reporting). **Proof of delivery is the wedge** — cryptographic evidence a specific call was fulfilled as specified, independently checkable. Nobody else surveyed in this space has built that layer. Trust layer is cross-cutting, not a third stacked layer — it applies across LMX Grid, not alongside it.
- **Distribution** — the four surfaces that make LMX Grid discoverable and callable: x402 Bazaar/Agentic.Market (protocol-level discovery), the MCP registry ecosystem (also the transport for the tool/function layer above — MCP does double duty, it's not purely a distribution channel), the ElizaOS plugin (runtime-specific), and LMX.Agent (the open template/scaffold, Track A). See "Phase 1 distribution goal" and "LMX.Agent" below for detail on each.

**Correction for the record (2026-07-11):** `x402bazaar.org` is *not* Coinbase's product — it's an independent, single-operator clone (GitHub user "Wintyx57") built on the open x402 protocol, near-zero traction observed (0 txns on its SKALE listing). Don't confuse it with the real CDP Bazaar discovery layer LMX lists on in Sprint 4. Its existence is still a useful data point: a bare directory + payment wrapper is trivially cloneable by one person in a weekend, which confirms neither layer alone is a moat and reinforces that verified delivery is the differentiated one.

**Explicit non-goals, restated so this doesn't drift again:** LMX does not compete with Bazaar as a directory. LMX does not compete with CDP Facilitator on payment verification. LMX does not claim to verify the *correctness* or quality of a third party's function output — only that the call happened and the response matched what was declared, hashed and timestamped, anchored on-chain. That precision matters for Week 3 legal: "verified delivery" is a defensible claim; "verified correct" is liability exposure for someone else's function that LMX shouldn't take on.

**Sequencing note, reaffirmed:** Phase 2 doesn't start until Phase 1's payment flow is fully live (Sprint 3 mainnet flip + Sprint 4 Bazaar listing). AWS's own history backs extra caution specifically on datasets — AWS Marketplace shipped in 2012, Lambda in 2014, but AWS Data Exchange (a dataset marketplace) didn't ship until 2019, thirteen years after launch, once the trust/billing/identity layer was completely proven out. Datasets stay explicitly out of scope for the same reason: no verification/anti-redistribution model exists yet for "prove a dataset was delivered without also enabling it to be copied and resold."

### Phase 2 Goal 1 — Storage routing (the "S3" of LMX)

**Split into two, 2026-08-20 — see "Storage, Vault, and LMX.Agent realignment" above for the full reasoning.** What was originally one goal turned out to be two different builds that had been getting conflated:

**Goal 1a — `lmx-tool-storage`, agent memory (active now, federated per 2026-08-21 Decision 4 above).** A Postgres-or-SQLite-backed metered KV/document store, `put(namespace, key, value)` / `get(namespace, key)` / `query(namespace, filter)`, same API shape as any `lmx-tool-*` — but self-hosted per agent operator, not run as one shared instance inside LMX's own `apps/tools/host`. Document shape: markdown files with YAML frontmatter (structured fields in frontmatter, prose + `[[wikilinks]]` in the body). `namespace = vault_id` — this is Vault's backing store (see `VAULT_PRIMITIVE.md`) and also what `lmx-agent-template`'s `state.ts` should be wired to once it's live. Own-namespace read/write is free, ungated, and local to the operator's own instance; cross-namespace access is Vault Phase B — x402-gated through Grid, Merkle-receipted, and fetched directly from the owner's own endpoint via a Grid-signed access grant, never proxied through or stored by LMX. What stays centrally hosted by LMX is only the manifest registry (`vault_id, owner_wallet, endpoint_url, permission_tiers, price`), pulled forward from Phase C in minimal, non-public form — see Decision 4. **Definition of done (Phase A):** a real namespace round-trips a note through the API, running on infra that isn't LMX's own tools host, own-namespace only, no gate. **DONE (2026-08-28)** — see Week 1 checkpoint note above for the verification detail.

**Goal 1b — decentralized archival storage (deferred, unchanged from original scope).** Route agent requests for large/durable file storage to decentralized networks (e.g. Filecoin, Arweave) the same way inference requests already route to io.net/Akash — same `ProviderAdapter` pattern, same per-call x402 pricing/verification, same receipt/Merkle anchoring for proof of delivery. This is bulk/archival blob storage, not agent memory — don't reopen the conflation. **Sequencing: after Goal 0 and after Goal 1a, not concurrent with either.** **Definition of done:** an agent can pay per-call (or per-byte/per-period) to store and retrieve data through LMX Cloud, routed to at least one decentralized storage network, with a verifiable receipt the same way inference calls get one today. **Convergence note (2026-08-21, doesn't change scope or sequencing):** Decision 4 above frames Goal 1a's self-hosted storage backend as eventually swappable for a genuinely decentralized one (IPFS/Ceramic-style) behind the same `endpoint_url` interface — that future backend and Goal 1b's decentralized-archival ambition are the same underlying substrate, even though the two goals stay functionally distinct (queryable agent memory vs. bulk archival blobs). Still sequenced after Goal 0 and Goal 1a, not pulled forward.

### Phase 2 Goal 2 — Callable function registry (Marketplace + Lambda, merged 2026-07-11)

**Sequencing: last of the three Phase 2 goals.** Definition pass done 2026-07-17, informed by the closest real precedent: Virtuals Protocol's Agent Commerce Protocol (ACP) — self-serve agent listing, escrow-based settlement, ~18,000 agents live. ACP's structure includes a formal **Evaluator** role: payment sits in escrow until a third-party evaluator agent verifies delivered work against a signed agreement — a real quality market, not just a delivery receipt. That's a genuine fork for LMX, not a detail: a richer trust product with real liability surface (ACP's model) versus the thin, legally clean delivery-proof LMX already committed to elsewhere in this doc ("verified delivery" is defensible; "verified correct" is liability exposure). **Decision: stay with the thin model for the MVP** — consistent with the lean, no-new-liability posture already established — but don't treat quality-evaluation as ruled out permanently; revisit once there's real marketplace volume, same as the deferred reputation/trust-scoring line below.

**Definition, answering the four open questions:**

1. **What's sellable (MVP-narrow):** only functions wrapping resources LMX itself routes and can observe — compute via `ProviderAdapter` (live) and storage once Goal 1 ships. Pure third-party webhooks are explicitly out of the MVP: LMX has zero visibility into what a third party's own backend actually did, so the receipt guarantee for those is closest to worthless of anything on this list. Not ruled out forever — just not at launch.
2. **Who can list:** the existing plan holds — Web3-1 wallet self-mint pattern, no human review, gated by the synthetic test-call check plus a refundable USDC bond sized high enough that spam-listing costs more than LMX's own verification overhead.
3. **What LMX guarantees, per tier (new — resolves the "is a thin guarantee sellable" question):** two explicit, differently-labeled tiers rather than one uniform claim. **"LMX-routed"** listings (compute/storage LMX executes directly) get the strong guarantee — LMX can attest routing, provider used, latency, and delivery. **"Third-party webhook"** listings (post-MVP, see above) get the thin guarantee only — a call was made, this exact response came back, hashed and timestamped, nothing about backend truth. Labeling this honestly in the registry UI, rather than presenting both identically, is what makes the thin tier still sellable instead of misleading.
4. **In-registry discovery vs. Bazaar:** the differentiator is integration friction, not reach. Bazaar requires an agent to speak x402 fresh to every new provider it discovers, protocol-wide. A function listed in LMX's own registry is callable through the same MCP surface and wallet/session an agent already has open with LMX — a "zero new integration" advantage for anything already inside LMX's ecosystem that Bazaar's broader-but-shallower reach can't offer.

**Revised framing:** originally scoped as two separate goals — "open the rails to other sellers" (Marketplace) and "widen job types routed" (the "Lambda" of LMX, see retired Goal 3 below). Collapsing these: a listed marketplace seller and a callable function are the same object once distribution runs through the MCP server. The MCP server (Phase 1 Goal 2, v1 shipped 2026-07-09) stops being "LMX's own 7 tools" and becomes a registry — any wallet-verified provider, including an agent itself, registers a function (manifest: description, input/output schema, price, endpoint), and any MCP-compatible agent discovers and calls it the same way it calls LMX's built-in tools today.

**Agents as first-class citizens, applied concretely:** the registrant doesn't have to be a company. This reuses the Web3-1 self-mint pattern (wallet-signed, no human review) — an agent good at some task can list its own skill and sell it to other agents. That's the differentiated end-state; every comparable product surveyed (CDP Bazaar, x402bazaar.org, RelAI) assumes sellers are companies and agents are only buyers.

**Anti-abuse, mechanical gates only, no human curation:** (1) a synthetic test call LMX makes once at registration to confirm the function responds and matches its declared schema before going live; (2) a small refundable USDC bond, slashed on verified bad behavior (schema mismatch, receipt anomalies, buyer disputes). Consistent with wallet-native self-serve onboarding — avoids reintroducing a human review bottleneck.

**Open technical question, unresolved:** for a function backed by a third party's own webhook (not LMX-routed compute), what can the receipt actually attest? LMX only sees what the provider chooses to return — the receipt can say "a call was made, this was the response, hashed and timestamped," nothing about the provider's backend. Whether that thin a guarantee is still a sellable trust signal is untested.

**Revenue model, open:** the old "LMX earns a cut of agent-originated revenue" assumed a marketplace take-rate on GMV. If LMX isn't routing the underlying resource — just settling and receipting a third party's call — a flat or usage-based infra fee (pricing the receipt/anchoring service itself) may be the more honest model. Decide before sizing Goal 2 revenue projections.

**Scope correction:** this is a bigger product commitment than Distribution Sprint 5's current sizing ("ship 7 tools, wire x402, get in registry"). "MCP is the flagship product" implies an ongoing surface — seller/listing dashboard, an in-MCP discovery tool (agents need to search LMX's own registry, not just Bazaar's), health monitoring on every listed function, a delisting/dispute flow. Not a sprint; a product line. Needs an explicit resourcing decision, not folded silently into Sprint 5/6 as currently scoped.

**Definition of done (revised):** a wallet-verified provider — human-operated or agent-operated — can register a function with a price and schema through LMX's MCP registry; any MCP-compatible agent can discover and call it through LMX's existing MCP surface; LMX settles payment (x402) and issues a delivery receipt, without vetting the function's output quality.

### Phase 2 north star, clarified (decided 2026-07-26)

Sprints 0/0b/1 (resource depth/breadth) are means, not the destination — the actual target is Sprint 2-6's output: a Mesh-scale marketplace (directionally 30+ listed agents, hundreds of callable tools, all x402-payable) plus LMX.Agent as the open framework layer developers build on. This is also explicitly where the demand-gen strategy shifts: once the registry exists, every new agent/tool shipped and listed is its own piece of marketing material (see Demand generation tactics below) — the same shape as Heurist's near-constant "Heurist x [Partner]" content pattern, applied to registry growth instead of partnership announcements.

**Calibration, stated honestly:** Heurist itself took roughly 1.5-2 years post-Mesh-launch, with an 11-13 person team and real capital, to reach ~30 agents / 100+ tools. The 12-month KPI target (double-digit active third-party listings, see KPI section) is a meaningful step toward that north star, not arrival at it — treat "Mesh scale" as a multi-year destination, not a 12-month deliverable, so the roadmap doesn't quietly reset expectations against a timeline nothing here actually supports.

**Access/payment model for every registry-listed function (mirrors what's already built, not new mechanism design):** the same dual/triple path already proven on the compute endpoint extends to third-party listings — (1) API key against a prepaid credit balance, human/dev-friendly; (2) direct x402 pay-per-call, no account or key at all, a wallet signs a payment per request against an HTTP 402 challenge — this is the actual machine-native path Phase 1's plumbing was built for; (3) MCP as a transport wrapping either of the above, so any MCP client (Claude Desktop, Cursor, Windsurf, or an autonomous agent) can call in. Every call, regardless of path, still gets a Merkle-anchored delivery receipt. Sprint 3's registry foundations work is "make every third-party function work this way," not a new payment mechanism.

**Open, unresolved — self-registration curation model:** researched 2026-07-26 how Heurist Mesh actually handles third-party contributions, since it's the closest real precedent for Sprint 3-4. Their model is GitHub pull requests (sometimes against posted bounty/integration-request issues) reviewed and merged by the Heurist team — real third-party revenue share, but human-curated, not permissionless. LMX's current Goal 2 spec (wallet-signed self-registration, mechanical-only anti-abuse via bond/slashing, deliberately no human review) is a harder, more ambitious version of what Heurist actually proved out. Not a reason to abandon the permissionless design, but a reason not to assume it's de-risked by Heurist's example — this piece is more experimental than the rest of the parallel suggests. Revisit explicitly during Sprint 2 scoping rather than assuming the original spec is validated.

**Resolved 2026-08-20 — flagship demo-agent vertical is the marketing agent.** See "Storage, Vault, and LMX.Agent realignment" above for the decision and the build sequence. The plan (confirmed 2026-07-26) was to build and list real demo agents on LMX's own stack as both marketing content and the literal proof-of-concept for Sprint 6's "one real agent-authored function" bar; three candidates were discussed below, kept for the record of why the other two were passed over:

This is the surface other things — other agent frameworks, other routers, researchers — can depend on without touching LMX's own execution path. This is the actual moat mechanism: composability lock-in, not the routing logic itself.
- **Closed:** the routing/scoring logic (how a request actually gets assigned to a provider) and the managed, authenticated, billed execution path — i.e., LMX Grid itself. This stays the product. Same split Infura draws between the open JSON-RPC spec and paid reliable node access.
- **Goal 2's registry** (callable function registry / MCP registry) is the natural home for the "open schema" half once built — a wallet-verified provider or agent registering a function is the same act as a third party depending on LMX's coordination layer.

**Value capture, two lines:** (1) the existing routing spread, reinforced — buyers can verify routing claims instead of trusting them, which is the credibility an anonymous agent needs before paying unprompted; (2) a new tiered-access line on the index itself (free/light query for adoption, paid for heavy/commercial use) — same shape as Etherscan's API or The Graph's hosted service pre-decentralization.

**Dependency worth naming:** the index's credibility compounds with provider count. Connects directly to the already-decided provider-depth priority (line ~100, "a third compute provider is a better use of that energy than starting Phase 2") — Aethir landing (Platform Sprint 0) isn't just a reliability-chain improvement, it's what makes the eventual open index a real claim instead of a two-network anecdote.

**Not new engineering scope.** This reframes Goal 0/Goal 0b/Goal 2 as already sequenced; it does not move up the Phase 2 gate.

### Case study: Ocean Protocol / Ocean Network (added 2026-07-24)

**Why this is the closer comparable than Infura alone:** Ocean Protocol's original datatoken/marketplace contracts are genuinely open — Apache-licensed, forkable — with fee capture enforced at the smart-contract level: every datatoken consume/trade fires a community fee plus an LP/marketplace-operator fee automatically, regardless of which frontend (Ocean Market or a fork of it) mediated the call. That's a stronger form of "open" than LMX's current L4 design above: the reliability/pricing index and proof endpoints are an open *query schema* over internally-computed telemetry (the Infura flavor — open spec, centrally hosted), not a redeployable protocol with fee logic baked into the contract itself (the Ocean flavor). Nothing today stops a third party from scraping the free tier or mirroring the schema once it's documented.

**Ocean Network (oncompute.ai, beta launched March 2026)** is the more direct structural analog to LMX as a whole, not the older data-marketplace story: open P2P compute-coordination concept underneath, but the actual monetized surface is the Orchestrator (a VS Code/Cursor/Windsurf extension) plus rented Aethir GPU supply on a pay-per-use escrow settled on Base — their own router-and-gateway-for-demand layer, same shape as LMX Grid (routing/scoring + managed billed execution).

**Validates the demand-first L0/L1 sequencing (below):** OCEAN's original curation-staking model was replaced by Data Farming for the same "mercenary capital" reason LMX is deferring L0 — and in October 2025 the Ocean Protocol Foundation withdrew from the Artificial Superintelligence Alliance (the OCEAN/FET/AGIX merger), citing Fetch.ai/SingularityNET violating asset-control commitments amid FET's ~93% price decline; OCEAN has since de-pegged and trades independently again. A live, recent instance of the token-first-liquidity trap this roadmap already names as the reason to hold L0 until L4 demand is proven — not a hypothetical.

**Open question this raises, unresolved as of 2026-07-24:** whether LMX's open layer should capture value the way Ocean's does — a small fee enforced at the protocol level on every consume event, not a bolt-on API access tier. John is leaning toward this. The concrete path that doesn't require a token or a new contract: reuse the already-built x402 rails (same CDP-facilitator/Base settlement already proven on `chat.ts`) on the reliability index and proof endpoints themselves, so programmatic/heavy third-party consumption settles a per-call micropayment enforced by middleware — not just documented as a paid tier. Casual/discovery-level access (StatusPage viewing, occasional proof lookups) would stay free, mirroring how Ocean's mandatory fee is small enough not to deter normal usage. Not yet designed or built — flagged here as the live direction, not a decision.

### L0/L1 — directional signal only, not an active workstream (decided 2026-07-20)

**The end-state ambition, named explicitly for the first time:** own the full stack — native L0 DePIN compute supply, an eventual L1/value-accrual layer that real transaction value flows through, the L4 coordination protocol above, and the existing L7 application surface. L0 native supply isn't pursued for its own sake — it's pursued so real DePIN transaction volume eventually flows through something LMX itself owns at the settlement layer, rather than LMX only ever taking a spread on other networks' supply.

**Deliberately sequenced last, and deliberately inverted from the standard DePIN playbook.** Most L0/L1 networks bootstrap supply first with token emissions and hope demand follows — the "mercenary capital problem": supply that leaves once incentives decline because there was never real usage underneath. LMX's plan is demand-first — prove real, unprompted demand at L4 before touching L0, so any eventual supply-side token design can be backed by real fee revenue instead of speculative inflation.

**Two open questions, deliberately unresolved today:**
- Whether "L1" means a literal sovereign chain (validators, consensus, a security budget — a categorically bigger undertaking) or a value-accrual token/treasury layer that doesn't require securing a new base chain.
- The trigger for moving from "L4 + demand" into active L0 investment — left open today as a directional signal, not a scheduled milestone.

**Named risk, not hypothetical — there's a live precedent in this same document.** The attorney legal review sat undefined and "worth revisiting" for weeks before being deferred three separate times (POM section). An L0/L1 trigger left permanently vague risks the same fate — always less urgent than whatever's directly in front of it. Not resolving this today by design, but flagging it so it doesn't quietly become "never."

**Explicitly not active right now:** no L0 hardware/incentive design, no token design, no chain decision. Only L4 (the reframe above) and demand generation (section above) are live workstreams — consistent with, and an extension of, the native-token deferral already recorded under "Explicitly not being built right now."

- **`apps/web/src/lib/notifications/`** (what the screenshot shows) — entirely client-side, computed only while a user's browser has the console tab open, from `/v1/status` and `/v1/keys`. Three derived kinds (provider health, low balance, key expiring), read-state in localStorage per browser. No sender identity anywhere (renders as impersonal system text), no delivery channel of any kind. The empty state is accurate, not broken.
- The still-open 2026-07-15 "Notifications — deferred" item under Housekeeping (line ~543) is a **different, separate gap** — push on settled payments / new-wallet events for the ops dashboard, not this user-facing panel. Not part of this decision.

**Corrected same day, 2026-09-10 — John clarified "LMX Ops" is literally `apps/ops`, his own admin dashboard, not a brand persona to invent.** The real ask: a way to compose and send notifications from that dashboard, plus a defined taxonomy of what users receive. Revised scope below supersedes the "separate persona" framing above — that framing came from treating "LMX Ops" as a cosmetic label choice before the actual workflow question was asked.

**User-facing notification taxonomy (four kinds):**
- **Welcome** — one-time, auto-delivered when an account is created. Content editable by John (a template row, not a hardcoded string) but the send trigger is automatic.
- **Account/system alerts** — automatic, no authoring needed: low balance, API key expiring/expired (already built, `derive.ts`), plus provider/platform health (the third existing derived kind — platform-wide rather than per-account, kept in this bucket for now).
- **Product updates** — authored by John in the new Notification Center, about features/models/fixes shipped.
- **Company updates** — authored by John in the same place, broader company news. Same authoring flow as product updates, separate kind so users can tell them apart.

**Workflow:**
1. **Author in `apps/ops`** — new "Notifications" page (the Notification Center), ops-auth gated like the rest of `apps/ops`. Compose: kind, title, body, optional link. MVP: broadcast to all users, send immediately — no segmentation or scheduling yet. Also shows send history.
2. **Store in Postgres** — new `notifications` table (raw SQL via `apps/api/src/db/migrate.ts`, same pattern as the rest of the schema — no ORM in this codebase). Authored/broadcast kinds are real rows; account alerts stay computed-live, not stored, since they're just current-state checks.
3. **Deliver** — one unified `GET /v1/notifications` endpoint (user-authenticated) merges stored authored notifications with the live-derived account alerts into the same `NotificationEvent` shape the console already uses. Everything in it displays under the LMX Ops identity — accurate now, since LMX Ops (the dashboard) genuinely is where the authored half originates, and the derived half is the platform's own automated monitoring.
4. **Read state** — authored notifications get real server-side read tracking (`notification_reads`: user id, notification id, read_at) so it survives across devices/browsers, replacing the current localStorage-only approach for that half. Derived alerts keep local fingerprint-based read state as today.
5. **Welcome trigger** — on account creation (the same four creation paths already wired to the Telegram `notifyAccountCreated` ping), also insert a welcome notification row targeted at that new user.

**Still explicitly deferred:** real email/push delivery outside the console (same reasoning as before — infra-heavy relative to current DAU), and audience segmentation/scheduling in the Notification Center (ship broadcast-only first). Also not touching the separate, still-open ops-dashboard payment-push item above.
